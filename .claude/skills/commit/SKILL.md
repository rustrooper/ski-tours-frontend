# Коммит в ski-tours-frontend

## Шаг 1. Собрать контекст (одним блоком, параллельно)

```
git status
git diff              # незастейдженные изменения
git diff --staged     # уже застейдженные
git log --oneline -10 # стиль последних сообщений
```

Читай **весь** diff, а не только имена файлов — сообщение должно описывать
суть изменения, а не список файлов.

## Шаг 2. Решить, что стейджить

- Если что-то уже застейджено пользователем вручную — **не трогай stage**,
  коммить ровно то, что он выбрал. Об остальном упомяни в отчёте.
- Иначе стейдж явными путями. `git add -A` — только когда убедился, что в
  untracked нет мусора.
- **Никогда не коммить:** `.env*`, ключи/токены/пароли, `node_modules/`,
  `.next/`, дампы, скриншоты и временные файлы. Заметил такое в untracked —
  не стейдж, скажи об этом пользователю.
- Изменения логически разнородные (например, правка секции + обновление
  зависимостей + конфиг деплоя) → делай **серию атомарных коммитов**, стейджа
  файлы по группам.

Работай в текущей ветке. Новых веток не создавай — в этом проекте коммиты в
`main` это норма.

## Шаг 3. Сообщение

Формат — **Conventional Commits, английский язык**, повелительное наклонение,
без точки в конце, subject ≤ 72 символов.

```
<type>(<scope>): <краткое описание>

<тело — только если "почему" не очевидно из subject>
```

**Типы:** `feat` `fix` `refactor` `perf` `style` `docs` `test` `build` `ci` `chore`

**Scope** — по фактической структуре репозитория, например:
`sections`, `layout`, `ui`, `lib`, `deploy`, `deps`, `config`

Примеры для этого проекта:

```
feat(sections): add autoplay to reviews carousel
fix(layout): prevent header overlap on mobile
refactor(ui): move base components to components/ui
chore(deps): bump next to 16.2.6
```

Правила:

- Описывай **что меняется и зачем**, а не «fixes», «refactoring», «updates».
  В истории такие сообщения есть — не повторяй их.
- Тело добавляй только при реальной необходимости (неочевидная причина,
  breaking change, ссылка на issue). Не пересказывай diff.
- **Не добавляй** `Co-Authored-By`, ссылки на Claude Code или эмодзи.

## Шаг 4. Коммит

Многострочное сообщение — через heredoc:

```bash
git commit -m "$(cat <<'EOF'
feat(sections): add autoplay to reviews carousel
EOF
)"
```

### Husky — обязательно к соблюдению

В проекте настроен `core.hooksPath = .husky/_`, хук `pre-commit` выполняет:

```
pnpm typecheck          # tsc --noEmit по ВСЕМУ проекту
pnpm exec lint-staged   # eslint --fix + prettier --write по staged-файлам
```

- **Никогда не используй `--no-verify`, `-n` или `HUSKY=0`.** Проверки должны
  отработать. Если пользователь сам просит обойти хук — тогда можно.
- lint-staged **изменяет файлы** и сам возвращает их в индекс. Поэтому после
  успешного коммита содержимое файлов может отличаться от того, что ты стейджил
  — это ожидаемо, не «откатывай» обратно.
- Хук упал → коммита **нет**. Прочитай вывод и разбери причину:
  - **ошибка `tsc` в файле, который ты не менял** — это существующая проблема
    проекта. Не чини её молча и не расширяй коммит. Сообщи пользователю, какой
    файл ломает typecheck, и спроси, что делать.
  - **ошибка в твоих изменениях** — исправь, пересобери stage (`git add` по тем
    же путям, т.к. lint-staged мог уже переписать файлы) и повтори коммит.
  - Не более **двух** попыток. Дальше — стоп и отчёт пользователю с реальным
    выводом хука, без приукрашивания.

## Шаг 5. После коммита

- `git status` — убедиться, что дерево в ожидаемом состоянии.
- В отчёте: короткий хэш, subject, что осталось незакоммиченным.
- **`git push` не выполнять**, пока пользователь явно не попросил. Если попросил
  — пушить в текущую ветку (`git push`), при отсутствии upstream —
  `git push -u origin <branch>`.

## Чего не делать

- Не менять код «заодно» — коммитим то, что есть.
- Не делать `git commit --amend` и не переписывать историю без явной просьбы.
- Не делать `git checkout`/`git restore`/`git reset --hard` по файлам
  пользователя ради «чистого» коммита.
