# Pull request в ski-tours-frontend

Репозиторий: `rustrooper/ski-tours-frontend` (origin, HTTPS). Инструмент — `gh`.

## Шаг 0. Разобрать аргументы

Из запроса нужно вытащить две вещи:

- **title** — название PR. Берётся у пользователя **дословно**, не переписывай
  и не «улучшай». Кавычки вокруг снимай.
- **base** — ветка, **в которую** делается PR (цель мержа).

Как разбирать:

- `/pr "Add reviews carousel" main` → title = `Add reviews carousel`, base = `main`.
- Явные формы `--base main`, `в main`, `into main`, `-> main` имеют приоритет.
- Токен без кавычек, совпадающий с существующей веткой (`git branch -a`) —
  это base, а не часть title.
- Не указан **base** → считай `main`, но скажи об этом в отчёте.
- Не указан **title** → предложи 2–3 варианта через `AskUserQuestion`,
  сформулировав их из коммитов ветки. Не придумывай молча.

Head-ветка (**из которой** PR) по умолчанию — текущая, её пользователь обычно
не называет.

## Шаг 1. Preflight (одним блоком, параллельно)

```
gh auth status
git status
git rev-parse --abbrev-ref HEAD
git branch -a
git fetch origin
```

Стоп-условия — не продолжай, доложи пользователю:

- **`gh` не авторизован** → скажи выполнить `gh auth login` и останови работу.
  Сам `gh auth login` не запускай, он интерактивный.
- **Незакоммиченные изменения** в файлах, относящихся к PR → не коммить их
  сам. Скажи пользователю и предложи скилл `commit`. Постороннему мусору в
  untracked (`.env*`, дампы, скриншоты) не давать попасть в ветку.
- **base не существует** ни локально, ни на origin → перечисли реальные ветки
  и спроси, какая имелась в виду.

## Шаг 2. Head-ветка

Если текущая ветка **не** равна base — работаем в ней, ничего не создаём.

Если текущая ветка **совпадает** с base (в этом проекте частый случай: коммиты
легли прямо в `main`):

1. Проверь, есть ли что вообще пушить: `git log origin/<base>..HEAD --oneline`.
   Пусто → PR делать не из чего, стоп.
2. Создай ветку на текущем коммите: `git switch -c <новая-ветка>`.
   Имя — в стиле репозитория: префикс `ski-tours/` + kebab-case суть
   (`ski-tours/reviews-carousel`).
3. Локальный `main` при этом остаётся на тех же коммитах. Скажи об этом и
   **спроси**, откатывать ли его на `origin/main` (`git branch -f main origin/main`).
   Без явного «да» — не откатывай.

`base` никогда не должен оказаться head-веткой PR.

## Шаг 3. Собрать описание

```
git log origin/<base>..HEAD --oneline
git diff origin/<base>...HEAD --stat
```

Читай сам diff, если по subject'ам коммитов суть не ясна. Проверь наличие
`.github/PULL_REQUEST_TEMPLATE.md` — если появится, заполняй его вместо
своей структуры.

Тело PR — **на русском** (проект ведёт один разработчик), коротко и по делу:

```markdown
## Что сделано

- пункт по каждому смысловому изменению, а не по каждому файлу

## Зачем

Одна-две фразы — только если это не очевидно из «Что сделано».

## Как проверить

- шаги/страницы, где видно результат (для UI-изменений — обязательно)
```

Правила:

- Не пересказывай diff построчно и не перечисляй все затронутые файлы —
  для этого есть вкладка Files changed.
- Пустые секции удаляй, а не оставляй с «—».
- **Не добавляй** упоминания Claude Code, `Co-Authored-By`, эмодзи.

## Шаг 4. Создать PR

Пуш ветки с upstream:

```bash
git push -u origin <head>
```

Тело — через файл, чтобы не воевать с кавычками и переводами строк в PowerShell.
Пиши его в scratchpad-директорию сессии (не в репозиторий), затем:

```bash
gh pr create --base <base> --head <head> --title "<title>" --body-file <path>
```

- Пользователь просил черновик → добавь `--draft`.
- **Никогда** не используй `--fill` (перезатрёт заданное название) и
  `--no-verify` при пуше.
- PR из этой ветки в этот base **уже существует** (`gh pr list --head <head>
--base <base>`) → нового не создавай. Запушь новые коммиты, при
  необходимости обнови название через `gh pr edit --title "<title>"` и верни
  ссылку на существующий PR.

## Шаг 5. Отчёт

- Ссылка на PR (`gh pr view --json url -q .url`).
- `<head> -> <base>`, число коммитов, название.
- Что осталось незакоммиченным и что ты решил за пользователя (например,
  base по умолчанию или сгенерированное имя ветки).

## Чего не делать

- Не мержить PR (`gh pr merge`), не закрывать и не ревьюить его.
- Не пушить напрямую в `main`/base и не делать `git push --force`.
- Не менять код «заодно» и не коммитить за пользователя — только пуш + PR.
- Не переписывать историю (`rebase`, `amend`, `reset --hard`) без явной просьбы.
- Не создавать релизы, теги и issue.
